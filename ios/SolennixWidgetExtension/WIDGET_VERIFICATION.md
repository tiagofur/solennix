# Widget Cross-Process Verification (REQ-WDS-02)

This document is the **codesigned manual success gate** for the iOS widgets'
shared `App Group` data flow. It complements the automated in-process round-trip
proxy (`SolennixWidgetExtensionTests/WidgetDataRoundTripTests`) which proves the
data layer writes and reads the same `UserDefaults` suite *within one process*.

> **REQ-WDS-02 (amended).** The cross-process round-trip (app writes → widget
> extension reads in a *different* process) is verified by a codesigned build run
> on a device/simulator. `UserDefaults(suiteName:)` returns non-nil even without
> the entitlement, so a real cross-process write→read is the only honest proof.
> The automated proxy covers the data layer; this manual gate covers the process
> boundary.

## Why a manual gate

WidgetKit runs the widget extension in its **own process**. A unit test in the
app target cannot reach extension-process reads, and the extension product
cannot be linked by a test bundle. A codesigned install is the only way to
observe the app and the widget reading the **same** `group.com.solennix.app`
backing store across processes.

## Prerequisites

- A codesigned build of **both** the app (`Solennix`) and the widget extension
  (`SolennixWidgetExtension`) against the same team/provisioning profile.
- `com.apple.security.application-groups` = `group.com.solennix.app` present in
  BOTH targets' entitlements (`project.yml` inlines it; the `.entitlements`
  files are regenerated by XcodeGen).
- A real device **or** the simulator (the simulator does honor App Groups, so it
  is sufficient for this gate).

## Procedure

1. **Clean install** the codesigned app on a device/simulator.
2. **Sign in** with a real account.
3. **Add a widget** to the Home Screen (and Lock Screen):
   - Upcoming Events (Small / Medium / **Large**)
   - KPI (Small / Medium)
   - Active Event (Interactive, Medium)
   - Lock Screen (Circular / Rectangular / Inline)
4. **Observe initial render.** With no data yet, each widget shows the **empty**
   state (`WidgetStateView`) — a themed icon + "No data yet", never a blank
   rectangle.
5. **Create an Event** in the app (confirmed, future-dated).
6. **Return to the Home Screen.** The Upcoming Events, Lock Screen, and Active
   Event widgets reload (via `WidgetCenter.reloadTimelines(ofKind:)`) and show
   the new event within ~15 minutes (or immediately on `WidgetCenter` reload).
7. **Register a Payment** against that event. Return to the Home Screen → the
   **KPI** widget's *Pending* value reflects the payment (the event amount
   **minus** what was paid).
8. **Sign out.** Every widget switches to the **signed-out** state — no previous
   user's data is shown.
9. **Change device language** (Settings → General → Language). A widget reload
   fires (`NSLocale.currentLocaleDidChangeNotification`) and strings localize.

## Acceptance criteria (all must pass)

- [ ] Step 4: empty state renders for every family (no blank rectangle).
- [ ] Step 6: an event created in the app appears in the event widgets.
- [ ] Step 7: the KPI *Pending* figure subtracts registered payments.
- [ ] Step 8: signing out renders the signed-out state with **no stale data**.
- [ ] Step 9: language change localizes widget strings.

## Failure triage

| Symptom | Likely cause |
|--------|--------------|
| Widget shows empty state right after sign-in + data load | App Group entitlement mismatch between targets, or the app didn't call `WidgetSyncCoordinator.syncAll()` |
| Data appears in the app but never in the widget | `group.com.solennix.app` not entitled on the extension; cross-process read fails silently |
| Stale data after sign-out | `setAuthState(.signedOut)` not called before `clearWidgetData()`, or the widget timeline not reloaded |
| Blank rectangle (Medium Upcoming Events) | Regression of REQ-WP-02 — the empty branch must route to `WidgetStateView` |
